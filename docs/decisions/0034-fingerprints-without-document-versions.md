# 0034: Item fingerprints without document versions, and one choice of cited copy

Status: accepted (maintainer request for hardening, 2026-11-03); the HTML rule in `reparse` is a proposed default
Date: 2026-11-03
Related decisions: [0004](0004-source-first-storage.md), [0024](0024-verbatim-item-summaries.md) (amended), [0026](0026-staff-reports-for-every-agency.md), [0032](0032-publish-irregular-agendas.md)

## Context
An agenda item's `source_fingerprint` hashed its title, section, and citations, and each citation names the document version it quotes. Staff report mappings, attachment lists, Claude summaries and topic tags are keyed on it, and a new fingerprint marks the item "revised" for residents and appends a `summary_versions` row. So two things that do not change an item changed every fingerprint of a meeting:

- **A file posted again.** El Dorado posted an unchanged agenda PDF again; the new version ID changed every fingerprint and hid the summaries until `summarize-items` learned to rebind them.
- **The same text cited from another copy.** A meeting can store the same agenda more than once: a PDF and its HTML agenda, or a copy an earlier discovery pass stored under another ID (the October 20 verified-candidate lists, decision 0033) beside the copy the listing names now. Capture parsed the documents in discovery's order and reparse in document ID order, and both kept the first copy that parsed, so they could cite different copies. A forced reparse on 2026-11-03 (to fill `full_title`) moved 77 Douglas County items in three past meetings to the other copy, marked them revised, and made two Claude summaries stale. Capture also reads items from an HTML agenda's markup, which a reparse of stored text cannot reproduce, so a reparse moved such items to the PDF's reading and the next capture moved them back.

Read-only production queries on 2026-11-03 found the churn was repeated, not a single event: of 1,389 fingerprint changes recorded in `summary_versions` since 2026-10-20, 1,009 kept every cited page and quote and changed only the document version; 362 items in nine agencies (Douglas County, Placer County Transportation, South Tahoe PUD, Washoe County, El Dorado County, South Lake Tahoe, Truckee, and others) had returned to a fingerprint they held before, A to B to A. Sixteen meetings held two current documents at one URL and 29 two documents with identical bytes. No item cited a document version that was no longer current.

## Decision
- **The fingerprint is what the item says.** `item_fingerprint` hashes the title, section, and each citation's page number and quote, without the document version. A file posted again, or the same pages and quotes cited from another copy, keeps every fingerprint: nothing is marked revised, mapped, summarized, or classified again, and no history row is written. Ingest moves the item's citations, its agenda excerpt's, and a Claude summary's requested-action citation to the new version; a summary whose quote is not on the same page of the new version is unbound from the fingerprint, which hides it until `summarize-items` rebinds or rewrites it. A change to the title, section, or a cited quote or page is still a revision. A change elsewhere on the page is not: the export rereads requested actions from the current page, a new document version still rescans staff reports, and what the model is sent still decides whether a summary is requested again.
- **One choice of cited copy.** `agenda.parse_agenda` tries copies in an order derived from the documents themselves (discovery's agenda-first ranking, then document ID), whatever order the caller lists them in, and prefers the copy the meeting's stored items cite while it is current and reads the same items (`prefer`, from `core.cited_documents`). Capture, the scheduled run's reparse of stuck meetings, `reparse --force`, and `backfill` (which uses capture) all go through it. The agenda is still preferred to the packet, and then the copy with the most items, before the cited copy.
- **Reparse leaves HTML-read items alone** (proposed default). A meeting whose items cite an HTML document is reported under `kept` and not reparsed, because capture reads those items from the page's markup, which is not stored. A capture rereads it.
- **Deploying changes no item.** `init_db` runs `migrate_fingerprints` once (recorded in `ingest_migrations`): every item whose stored citations reproduce its stored fingerprint under the old formula takes the new one, in the same transaction as the rows derived from it (`summaries`, `item_staff_reports`, `item_attachments`, `ai_item_summaries`, `ai_topic_classifications`), and each staff report scan that was current gets its recomputed key, so no meeting is mapped again. An item whose citations failed validation stores none to recompute from; ingest moves it, and its derived rows, the next time it reads the same citations. On a copy of the local database the migration moved 2,182 of 2,286 items, left every derived row bound, changed no `change` or `updated_at`, and kept the export valid; a second forced reparse of eleven agencies then changed nothing.

## Alternatives and consequences
Fixing only the choice of copy was not enough: a re-post still changes the version ID, and a meeting with a stale duplicate copy still switches once when the listing stops naming it. Hashing the source document ID (not the version) was rejected, because the PDF and the HTML copy of one agenda have different IDs. Recomputing fingerprints lazily on each capture alone was rejected: settled past meetings are rarely captured again, so their derived rows would stay under two formulas for months.

"Revised" now means the item's own text changed, not that its agenda file did. Both Cloud Run jobs must run the new image (decision 0030 rolls out both together): an older worker would compute the old formula and mark items revised, which the new worker then moves back without a revision. `summary_versions` rows written before the migration keep the old fingerprints.

## Revisit when
An agency's copies differ in page numbering for the same text (a packet that reprints the agenda on other pages), or a resident-visible change elsewhere on an item's page needs to count as a revision.
